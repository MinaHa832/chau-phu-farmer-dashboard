# 실제 계정과 공용 기록 연결

## 이메일 없이 함께 시연하기

메일 계정이나 SMTP 없이도 첫 화면에서 **농민·현장 관리자·펌프 운영자** 시연 계정을 고를 수 있습니다. 농민은 54개 시범농가 중 하나, 운영자는 18개 RMU 중 하나를 선택합니다. 비밀번호를 만들거나 이메일을 확인하지 않습니다.

이 기능은 공개된 가상 역할을 선택하는 시연입니다. 실제 사용자의 신원을 인증하는 계정이 아니며, 누구나 다른 시연 역할을 선택할 수 있습니다. 실제 개인정보를 입력하지 않습니다.

아래 운영용 기본 마이그레이션 뒤에 **migrations/202611260002_shared_demo.sql**, **demo-seed.sql**을 순서대로 실행합니다. Vercel 연결 변수는 운영 기능과 같으며 별도 비밀 키가 필요하지 않습니다. 원래의 54개 시범농가 정의를 별도의 비공개 스키마에 생성하고, 시연에 필요한 공개 함수만 허용합니다. 실제 농가 수정본·계정·기록을 시연 공간으로 복사하지 않습니다. 시연 권한으로 실제 계정 승인을 할 수도 없습니다.

관리자는 **54개 농가 전체 시연 → 공유 계획 관리 → 현재 관개 계획 공유**로 가상 공급량과 배분안을 공유합니다. 농민이 자기 주차의 급수를 요청하고 운영자/관리자가 실급수량을 기록하면 농민 화면에도 반영됩니다. 같은 시연 계정의 기록은 기기 간 공유됩니다. 시연 접속은 8시간 동안 유지되며 **역할 바꾸기**로 나갈 수 있습니다.

운영용 이메일 인증은 아래 절차대로 별도로 연결합니다. 시연을 위해 운영용 이메일 확인을 끄지 않습니다. 배분·처리 규칙을 변경할 때는 비공개 시연 함수에도 같은 규칙을 반영하는 후속 마이그레이션과 분리 검사를 추가합니다.

운영 연결에는 사용자가 소유한 Supabase 프로젝트가 필요합니다. 앱은 이메일·비밀번호를 Supabase Auth로 확인하고, 로그인한 계정의 권한을 PostgreSQL에서 다시 확인합니다. 인증 서비스나 데이터베이스가 준비되지 않은 상태를 운영 완료로 간주하지 않습니다.

## 1. 새 프로젝트 준비

[Supabase 프로젝트 만들기](https://supabase.com/dashboard/new)에서 프로젝트를 만듭니다. 데이터베이스 비밀번호는 직접 정하고 보관해 주세요. 채팅이나 GitHub에 올리지 않습니다.

SQL Editor에서 다음 파일을 순서대로 실행합니다.

1. `migrations/202611260001_shared_portal.sql`: 계정 배정, 요청, 급수, 신고, 편익, 변경 이력과 권한 규칙 생성.
2. `seed.sql`: 기존 규칙 그대로 RMU마다 3개, 총 54개 시범농가 등록. 재실행해도 기존 농가를 덮어쓰지 않습니다.

첫 번째 파일은 새 데이터베이스에 한 번 실행하는 마이그레이션입니다. 실패 시 오류를 해결한 뒤 다시 실행합니다. 트랜잭션이므로 중간 단계만 저장되지 않습니다. 두 번째 파일은 반복 실행할 수 있습니다. 기존 18개 경계 파일은 변경하지 않습니다.

## 2. 이메일 인증 설정

Supabase의 Authentication 설정에서 이메일 로그인을 사용하고 **Confirm email**을 켭니다. URL Configuration의 Site URL은 배포할 사이트 주소로 지정합니다. 미리보기와 운영 주소가 다르면 사용하는 주소를 Redirect URLs에도 등록합니다. 비밀번호 복구 링크도 이 사이트로 돌아옵니다.

운영용 이메일은 Supabase의 발송 제한을 확인하고 SMTP를 연결해야 합니다. 연결 전에는 허용된 테스트 수신자로 이메일 확인을 먼저 검증합니다. 이메일 확인을 꺼서 문제를 우회하지 않습니다.

## 3. Vercel 연결

대상 프로젝트는 `chau-phu-farmer-dashboard`, Root Directory는 `chau-phu-full-program-deployment`입니다. Vercel의 Settings → Environment Variables에서 아래 값을 직접 등록합니다.

| 이름 | 값 |
| --- | --- |
| `SUPABASE_URL` | Supabase 프로젝트의 Project URL |
| `SUPABASE_PUBLISHABLE_KEY` | 같은 프로젝트의 Publishable key (기존 프로젝트는 `SUPABASE_ANON_KEY`도 지원) |
| `PORTAL_REQUIRE_AUTH` | `1` |

Secret key·service_role key·DB 비밀번호는 이 앱에 필요하지 않습니다. Preview와 Production에 적용할 환경을 각각 확인하고 다시 배포해야 합니다. 운영 계정과 실데이터를 검증되지 않은 미리보기에 연결하지 않습니다.

설정이 전혀 없는 기존 배포는 명시된 기기 내 시연 화면을 유지합니다. 인증 설정이 일부라도 있거나 `PORTAL_REQUIRE_AUTH=1`이면 서버 연결 실패 시 로그인을 차단하며, 로컬 시연 권한으로 돌아가지 않습니다. API는 미설정 상태에서 공용 기록을 저장하지 않습니다.

## 4. 최초 관리자 지정

배포된 로그인 화면에서 예정된 관리자 이메일로 계정을 만들고 확인 메일을 엽니다. 가입만으로는 관리 권한이 생기지 않습니다.

이메일 확인 후 `bootstrap-admin.sql`의 `REPLACE_WITH_VERIFIED_ADMIN_EMAIL`을 실제 이메일로 바꾸어 SQL Editor에서 실행합니다. 이 파일은 **확인된 이메일**만 최초 관리자로 승인하며, 관리자가 이미 있으면 실행을 중단합니다. 개인정보를 넣은 사본은 GitHub에 올리지 않습니다.

이후에는 관리자의 **계정·공유 관리**에서 다른 계정의 접속을 승인하고 농민은 담당 농가, 펌프 운영자는 담당 RMU를 배정합니다. 선택 화면과 주소의 `role` 값은 권한을 부여하지 않습니다. 마지막 관리자는 화면에서 해제할 수 없습니다.

## 5. 함께 사용하는 순서

1. 관리자가 기존 캘린더에서 공급자료와 배분안을 검토하고 **계정·공유 관리 → 현재 관개 계획 공유**를 누릅니다. 가상 공급량은 가상 표시를 유지합니다.
2. 농민이 자기 농가·주차의 급수량을 요청합니다.
3. 담당 펌프 운영자와 현장 관리자의 요청 목록에서 같은 요청을 확인합니다.
4. 운영자가 처리 중·완료·부분 공급·공급 불가 상태와 실제 공급량·메모를 저장합니다.
5. 농민의 요청 목록과 나의 관개 일정에 처리 상태와 실급수량이 표시됩니다.

화면이 켜져 있으면 15초마다 최신 기록을 확인합니다. 창으로 돌아오거나 **새로 확인**을 눌러 즉시 확인할 수도 있습니다. 입력 중인 폼은 자동 갱신으로 덮어쓰지 않습니다. 다른 기기에서 먼저 저장한 기록은 충돌로 알리고 다시 확인하게 합니다. 통신이 실패하면 저장 성공으로 표시하지 않습니다.

실측 주간 합계를 직접 등록한 경우 그 값을 우선하고, 요청별 공급량과 중복 합산하지 않습니다. 완료는 요청량 이상의 실급수량, 부분 공급은 그보다 적은 양을 입력합니다. 공급 불가·초과 공급은 사유가 필요하며, 종료한 요청은 관리자가 사유를 남겨 정정합니다.

기존 기기의 개인 저장 기록은 자동 업로드하거나 덮어쓰지 않습니다. 필요한 실제 농가·기록의 이전은 관리자 검토 후 별도로 진행합니다. 기존 등록 양식과 기기 내 시연 기능은 유지하며, 공용 모드에서 54개 시범농가 전체 삭제·교체는 차단합니다.

## 구현 검증과 운영 확인

`npm ci && npm test`는 PostgreSQL 엔진에서 권한·요청·처리·공유·수정 충돌을 검사합니다. HTTP 통합 테스트의 Auth 응답만 테스트 전용 모의 응답이며 실제 Supabase 이메일 발송·로그인을 증명하지는 않습니다. 운영 연결 후에는 서로 다른 기기의 실제 승인 계정으로 위 1~5번을 다시 확인해야 합니다.

개인정보는 로그인한 계정의 배정 범위로 제한합니다. 펌프 운영자에게 신고 원문·신고 농가·신고 처리 메모를 내려주지 않습니다. 일반 계정의 테이블 직접 접근은 차단하고, 서버와 데이터베이스의 변경 이력은 같은 트랜잭션에 기록합니다. 편익 검증은 입력자와 다른 관리자가 해야 하며 검증 완료가 자동 지급을 뜻하지 않습니다.
